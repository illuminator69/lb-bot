# Session summary — 2026-08-05/06

Two pieces of work, in order: a performance pass on the web UI, then five rounds
of debugging the source search that pass had helped break. Both are merged to
`claude/unraid-containers-handoff-egnevy` and verified against the live stack.

Outcome: source search works on albums where it never had, and the UI is
"much snappier" (user's words) — no more minute-long waits or whole-screen
freezes.

---

## Part 1 — Performance (`a7ff079`, merged `b3448a0`)

Reported symptoms: finding sources took ~60s; starting a search on album B while
album A was searching made B slow too; returning to album A was slow again;
artist pages slow; "everything feels stale".

Three independent causes, all self-inflicted:

1. **A process-wide lock held across a 60s network call.** `_group_sources_task`
   held `_review_lock` for the whole slskd search. Every `/api/summary`,
   `/api/gaps` and `/api/gaps/<id>` poll — every 2s — waits on that lock, so one
   album's search froze the entire UI. Split into plan (locked) → search
   (unlocked) → apply (locked), with `_group_generation` to detect a rescan
   landing mid-flight.
2. **The search result was computed and thrown away.** `created_at` was written
   and never read; there was no reuse at all. Added `SOURCE_RESULTS_TTL` (180s)
   and a `force` flag for "search again".
3. **Multi-MB state deep-copied on every poll.** `_review_snapshot()` copied the
   whole review state — including every peer's file listing — to render eight
   scalar fields per row. Added `_review_list_snapshot()`; stripped the raw slskd
   payload from what gets persisted (24398 → 348 bytes in the disk test).

Also: connection pooling (`_http`, one `requests.Session` per host — there was
none anywhere), single-flight on `_nd_album_index`, and hoisting the full
Navidrome catalog fetch out of the per-artist loop in `_library_index_task`.

**Judged unavoidable and left alone:** Soulseek peer latency, MusicBrainz's hard
1 req/sec (`_mbz_lock`'s serialization is a correct implementation of it, not a
bug), and the state-file fsync. The MusicBrainz fairness gate — so a bulk index
build can't monopolise the rate budget ahead of an interactive page — was
deliberately **not** implemented and is still open.

## Part 2 — Why the source search surfaced nothing

Five rounds. Recording the wrong turns too, because the pattern in them is the
point.

### Round 1 — the album stranded itself (`0fdce29`, merged `c04f676`)

A finished search flips every approved track to `source_pending`, but that
decision was missing from `_RETRYABLE_DECISIONS`, so
`_approve_pending_missing_tracks` skipped it. Harmless while results were
persisted — but Part 1 stopped persisting them, so an album searched once had no
approved track left and every later search died on "No approved tracks". It sat
on "choosing a source" forever with nothing to choose. Fourteen albums were in
that state.

Verified live: `/api/tasks` said `Found 119 source(s)`; the group returned
`sourcesTotal 0` and answered "No approved tracks" to every retry.

The reason it took a live probe to find: **the search is a background task and
nothing rendered it.** A search in flight, one that found nothing, and one that
refused to start were indistinguishable from a dead page. Fixed by stamping
`group_id` on tasks, exposing `sourceTask` on the album detail and `searching` on
the rail row, and reporting peers/files/elapsed through a progress callback.

### Round 2 — peers that lock part of their share (`0321686`, merged `575d5c3`)

`_score_folder` compared slskd's **peer-wide** `lockedFileCount` against the
handful of files that peer returned for one query:

```python
if min(peer.lockedFileCount, raw_count) >= raw_count: return 0
```

A peer sharing 4,000 locked files who offers ten good FLACs computes
`min(4000, 10) >= 10` → score 0. Locking part of a share is normal on Soulseek,
so this eliminated most peers. It also sits *above* the guard block, so the
"pick best" fallback couldn't rescue it. Now counted per folder from
`lockedFiles`; the peer-wide number is display-only.

Confirmed live afterwards: King Krule — The Ooz went from 0 to **121 sources**,
ranks 1–5 all FLAC with full 19/19 coverage.

Also added here: an empty result must say *why*. `slskd_run_search` fills a
`stats` dict and `_no_source_reason` turns it into a sentence, stored on the
group so it outlives the task — and it sets `mp3_would_help`, which finally lets
the MP3 opt-in appear on evidence rather than only after a download has already
failed for want of an accepted file.

### Round 3 — one null-`files` peer sank the whole search (`2bc4d7b`)

slskd sends `"files": null` for a peer whose only hits were locked.
`peer.get("files", [])` returns `None` for those (the key is present), and
`for f in None` raised out of the response loop — **one such peer discarded all
139 others' results**, swallowed by the exception handler into a bare
`return []`. Same population as round 2: peers who lock part of their share are
exactly the ones who answer this way.

Also fixed here: `stats` was only filled on the *success* path, so all five early
returns reported an empty dict as "No peer answered the search" — about a search
that had just counted 139.

### Round 4 — a wrong theory, kept honest

Concluded the results were "counted but not yet published" and added a settle
wait. Partly right, but the sizing was wrong and I asserted a timing explanation
I couldn't support. The user's next result killed it: 63s elapsed, still nothing.

### Round 5 — the actual answer (`c7a05d5`)

Stopped inferring and shipped `GET /api/debug/slskd-search` (`e892f6c`), which
traces one search end to end using the bot's own API key. The trace:

| t | state | responseCount | `/responses` | `?includeResponses=true` |
|---|---|---|---|---|
| 5.1s | InProgress | 138 | 0 | 0 |
| 25.8s | InProgress | 143 | 0 | 0 |
| 35.4s | InProgress | 143 | 0 | 0 |
| 39.4s | **Completed, TimedOut** | 143 | **142** | **142** |

**slskd publishes nothing until the search completes, then publishes everything
at once.** `responseCount` ticks up live — that is what the progress line counts,
which is why a failing search could honestly report "143 peers" and surface
nothing. The two numbers come from different endpoints and only one was ready.

Consequences:

- The early exit added in Part 1 could never work. There is no partial result.
- `SEARCH_TIMEOUT` of 30s cut the poll off ~9s before the results appeared.
  Raised to **75s** as a safety cap sized to outlast slskd's straggler timeout.
- **"Why did it work before?"** It didn't, reliably. It worked for albums whose
  searches completed inside 30s (Pink Floyd, The Ooz) and never for ones with
  slow stragglers (Horsegirl, Cocteau Twins B-sides). Part 1 narrowed the window
  from 30s to ~6s and made it near-total, but the flaw predates it.
- The early-exit condition is kept, repurposed to the only thing it can do: once
  peers stop arriving, `PUT /searches/{id}` asks slskd to **wrap up**, so results
  publish sooner rather than being read sooner. Best effort — if the stop fails,
  the poll runs to the cap and still succeeds.

slskd-side filtering was ruled out at the same time: `filters.search.request` is
empty, and it governs incoming requests anyway.

## What to remember

- **Read the API before theorising about it.** Rounds 2–4 were all inference from
  the outside, and the pattern held: each explained the symptom plausibly and was
  wrong or incomplete. The probe answered it in one call. It is still there.
- **An unexplained empty result is a bug in its own right.** Every round here was
  slowed by the system knowing exactly why it had nothing and discarding that.
- **Treat every slskd collection as nullable**, and never compare a peer-wide
  count to a folder-local one.
- The user's insistence that the error message was "not the problem" was correct
  about priority and wrong about relevance — the message was pointing at the
  seam (two endpoints disagreeing) the whole time. Worth reading a bad message as
  evidence, not noise.

## Still open

- MusicBrainz fairness gate in `mbz_get` (bulk index builds monopolise the
  1 req/sec budget ahead of interactive page loads). Deliberately deferred.
- Searches now take ~40s again where the broken version claimed ~13s. If the
  `PUT` stop works, they should land nearer 10–15s; `&stopAt=6` on the probe
  measures it independently.
- `_load_review_state` drops `source_results` on restart by design (the file
  payload isn't persisted). Albums then need a fresh search — correct, but it is
  what turned the round 1 latent bug into a live one.
